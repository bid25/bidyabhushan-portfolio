## Abstract

Consumer tablets routinely outlive their vendor's software support. This paper describes **Zucchini Linux**, a bring-up of a near-mainline Linux 7.1.3 kernel with an Arch Linux ARM64 userland, alongside LineageOS 21, on the Samsung Galaxy Tab A 8.0 LTE (SM-T295, Qualcomm SDM429). The two systems are selected from a boot menu at power-on.

We contribute:
1. **A second-stage bootloader injection scheme** in which `lk2nd` is wrapped in a boot image that Samsung's S-Boot accepts, avoiding vendor device-tree overlay merging through an exact PMIC selector match while the factory bootloader stays unmodified (Section 4).
2. **A non-destructive storage mapping** that places an Arch root filesystem on the userdata partition, reuses Android partitions as swap and scratch space, and hands off to LineageOS through a warm reset with a Qualcomm reset cookie (Section 4).
3. **Peripheral enablement work**: a device tree for the SDM429's four-core topology, a DRM driver for the JD9367 (TXD) panel, a rotated 24-bpp shadow blitter for Xorg fbdev, and a PMIC power-off fix by direct SPMI programming (Section 5).
4. **A development record**: dated photographs of successes and failures, and preliminary measurements with their caveats (Sections 6-8).

Preliminary single-device measurements show **199 MiB** of memory in use at idle against **1,380 MiB** on stock Android 11, a cold boot to desktop in **11.2 s** against **34.6 s**, and **620 mW** desktop-idle draw. We include photographs taken during development and state the limits plainly: the photographed desktop session uses software rendering, the Android side runs with SELinux permissive, and the Knox warranty flag is tripped.

**Keywords:** mobile Linux · Qualcomm SDM429 · lk2nd · device tree · Samsung S-Boot · dual boot · embedded systems · hardware longevity

## 1. Introduction

Tablet hardware tends to outlast its software. The Samsung Galaxy Tab A 8.0 (2019) LTE (SM-T295, codename `gto`) pairs a Qualcomm Snapdragon 429 with 2 GB of LPDDR3 and 32 GB of eMMC storage. It shipped with Android 9 and its last official firmware is Android 11 (`T295XXS6CWG2`). Under that firmware, idle memory in use is about 1.4 GB of the 1.77 GiB available (Section 7), which makes the device sluggish for ordinary use even though its Cortex-A53 cores remain adequate for a light desktop.

Running a near-mainline Linux kernel on such a device is attractive but runs into four obstacles:

1. **Bootloader Validation & DTBO Merging:** Samsung's primary bootloader (S-Boot) validates boot-image structure and verified-boot footers and attempts to merge vendor device-tree overlays into the kernel it loads.
2. **Asymmetric CPU Topology:** The SDM429 exposes only four Cortex-A53 cores, while the base platform description assumes eight.
3. **Display Panel Ambiguity:** The display panel cannot be inferred reliably from the chassis stamping alone.
4. **Permanent Brick Risks:** Any approach that overwrites the factory bootloader risks a device that cannot be reflashed.

This paper makes the following contributions:

1. A bootloader injection scheme that runs `lk2nd` as a second stage from the boot slot, bypassing vendor overlay merging by matching the board's PMIC selector, with the factory `aboot` never written (Section 4).
2. A non-destructive storage layout and a warm-reset handoff that lets the same menu start either Arch Linux ARM or LineageOS 21 (Section 4).
3. Peripheral enablement for display, touch, power-off, USB gadget and connectivity, with the debugging method used to find each fault (Section 5).
4. A development record: dated photographs of successes and failures, and preliminary measurements with their caveats (Sections 6-8).

The two operating systems run one at a time; the boot menu selects which. We call this *dual boot*, not concurrent operation.

## 2. Background and Related Work

### 2.1 Android-hybrid and mainline approaches

Projects such as Ubuntu Touch and Sailfish OS use Halium or libhybris to run a GNU/Linux userland over the vendor's Android kernel, often a 3.18 or 4.9 branch. This retains proprietary GPU and camera stacks but ties the device to a vendor kernel fork that receives few updates. Mainline-focused projects such as postmarketOS instead target upstream kernels and open drivers, mostly on popular reference phones [1]. We are not aware of a public mainline bring-up for the SM-T295 or for Samsung's SDM429 LTE tablets.

### 2.2 lk2nd

`lk2nd` is an open-source second-stage bootloader derived from Little Kernel. It is loaded by the vendor bootloader as if it were a boot image, brings up a standard fastboot interface, and boots conventional Android boot images [2]. It supports a range of Qualcomm devices. Applying it here required accommodating S-Boot's overlay engine, signature trailer, and verified-boot structure (Section 4).

### 2.3 Samsung S-Boot

S-Boot hosts Samsung's Download Mode (the Odin protocol, also implemented by Heimdall), enforces image structure checks, and records a Knox warranty flag when non-Samsung software is loaded. Its on-screen failure messages, such as `SECURE CHECK FAIL : boot.img`, are the main feedback channel in early bring-up (Figure 5).

### 4.2 The PMIC selector

When S-Boot loads a boot image it checks whether the device tree already matches the board. If it does, it skips the vendor `dtbo` partition (`p26`); otherwise it overlays Samsung's vendor nodes onto the tree, which corrupts phandles on a mainline kernel. We extracted the selector values from the stock device tree and encoded them in the root node of `lk2nd`'s own tree:

```dts
/* lk2nd device-tree matching node for Samsung Galaxy Tab A 8.0 (SM-T295) */
qcom,msm-id = <0x162 0>;            /* SDM429 */
qcom,board-id = <0x08 0>;           /* MTP */
qcom,pmic-id = <0x10016 0x25 0 0>;  /* PM8953 + PMI632 */
```

With an exact match, S-Boot sets `dtbo_needed = false` and no vendor overlay is applied.

### 4.3 Boot image layout

S-Boot also checks image structure. The accepted layout is shown in Figure 2. An early standalone image failed with `SECURE CHECK FAIL : boot.img` (Figure 5a) because the assembly script zeroed the padding between the signature header and the 512 KiB boundary. Binary comparison against the last working image showed an internal AVB hash descriptor at byte offset 356,352 (`0x57000`) inside that range. Preserving the whole 0-512 KiB prefix of the working `lk2nd` image and placing the Stage-2 kernel at 512 KiB removed the failure.

### 4.5 Boot menu and the LineageOS handoff

The menu (Figure 3) lists EDL, Linux, Reboot, Lineage, Shutdown, Recovery (TWRP) and Fastboot, with a hardware telemetry panel below. Jumping from `lk2nd` straight into the Android kernel left the display in a half-initialized state, because `lk2nd` has already programmed the MIPI DSI controller while the downstream kernel expects a cold start.

The fix is a warm reset: the menu calls `reboot_device(RECOVERY_MODE)`, which writes the cookie `0x77665502` to shared IMEM (`0x0860065c`) and resets the PMIC. S-Boot reads the cookie and cold-boots the recovery slot (`p57`), which holds the LineageOS boot image.

## 5. Hardware Bring-Up

### 5.1 Debugging without a serial port

Early boots produced no display, no USB and no LED activity. Two mechanisms recovered information:

1. **Early Kernel Console:** Directed to BLSP1 UART2 at `0x78B0000` via command line arguments:
   ```bash
   earlycon=msm_serial_dm,0x78B0000 console=ttyMSM0,115200n8
   ```
2. **Persistent Ramoops Buffer:** A 1 MiB ramoops region at `0x92100000` (passed with `lk2nd.pass-ramoops`) preserved the kernel dmesg log across warm reboots. After a crash or warm reset, the log was extracted directly from `/sys/fs/pstore/console-ramoops-0` upon returning to `lk2nd`.

### 5.2 CPU topology

The SDM429 exposes four Cortex-A53 cores at MPIDR affinities `0x100`-`0x103`, while the inherited platform tree describes eight. The kernel tried to start the missing cores through PSCI and received error code `-22`, and `cpuidle-psci` refused to register idle states while any listed CPU lacked them. The device tree deletes the absent cores and rebuilds the CPU map:

```dts
/* Rebuilt CPU topology for Snapdragon 429 4-core cluster */
/delete-node/ &cpu0;
/delete-node/ &cpu1;
/delete-node/ &cpu2;
/delete-node/ &cpu3;

cpu-map {
    cluster0 {
        core0 { cpu = <&cpu4>; };
        core1 { cpu = <&cpu5>; };
        core2 { cpu = <&cpu6>; };
        core3 { cpu = <&cpu7>; };
    };
};
```

### 5.3 Display

**Panel identity.** The chassis stamping (`LD200709DA5`) suggested a Lead Display ILI9881C panel, but a driver for that controller produced DSI timeouts (`-110`). When `lk2nd` first booted on 18 October, `fastboot getvar all` returned:

```text
lk2nd:panel:qcom,mdss_dsi_jd9367_wxga_video_txd
```

also visible on the menu in Figure 3a. The panel is a Jadechem JD9367 in Tongxingda packaging, evidently a second-source part. A DRM panel driver with the correct DSI sequence (4-lane video mode, PM8953 rails L23 at 0.8 V and L6 at 1.8 V) was written, and a SimpleFB linear framebuffer provides the console.

**Rotation.** The panel is an 800×1280 portrait array; the desktop runs at 1280×800. Upstream `xf86-video-fbdev` disables rotation on 24-bpp framebuffers because pixels are not 4-byte aligned (stride 2,400 bytes). A patched shadow blitter, `fbdevUpdateRotate32to24`, renders into a 32-bpp landscape buffer and copies damaged rectangles into the 24-bpp portrait framebuffer using:

### 5.4 USB gadget and power-off

**USB.** The gadget controller deferred forever on a vbus regulator (`-EPROBE_DEFER`). The inherited tree referenced a phantom handle (`vbus-supply = <0x6f>`) although VBUS detection on this board goes through the PMI632 via `extcon`. Removing the handle and binding to `&pmi632_uusb` let the ChipIdea controller probe and the CDC ACM (serial) and NCM (Ethernet) functions appear.

**Power-off.** `poweroff` rebooted the tablet. S-Boot leaves the PMIC's `PS_HOLD_RST_CTL` register (SPMI `0x085a`) at `0x01` (warm reset), so dropping `PS_HOLD` restarts the SoC. Because the kernel lacked debugfs register writes, a root-only userspace daemon maps the SPMI write channel for APID 37 through `/dev/mem` at:

<div className="my-6 p-3 sm:p-4 border-2 border-[#0B3D2E] bg-[#FFFDF0] font-mono text-center text-xs sm:text-sm font-bold shadow-[3px_3px_0_#0B3D2E] overflow-x-auto max-w-full">
  <code>0x02400000 + 0x128000 = 0x02528000</code> &nbsp;&nbsp;&nbsp;&nbsp;(3)
</div>

and writes `0x84` (shutdown, enable) to `0x085a` before `PS_HOLD` is released. This produced the first full hardware power-off under Linux on this device. The boot log in Figure 6b also shows services that unbind a legacy `msm-restart` driver and bind a `PS_HOLD` driver for reboot, indicating the mechanism has evolved since this first fix.

All measurements are from one SM-T295 unit, one run per condition, by the author. Boot time is from power-button press to an interactive UI. Memory is used RAM at idle with Wi-Fi connected and no applications open. Power is read from the PMI632 fuel gauge at a nominal 3.85 V, and runtime is projected as 19.1 Wh divided by the draw. ## 8. Discussion

### 8.1 Security posture

Verified boot constrains the design. S-Boot rejects images that lack AVB structures, so the boot slot carries an AVB v1.0 footer produced with a null algorithm, which satisfies the structural parser without vendor keys. This means the boot slot is not cryptographically protected.

The Knox flag is tripped (Figure 3c), the Android build is signed with public test keys and runs with SELinux permissive, and a serial console is enabled (Figure 7c). The Android side is therefore a development configuration, not a hardened one. `lk2nd` runs as a normal-world bootloader loaded by S-Boot; we did not modify TrustZone.

### 8.2 Upstreaming

The device tree uses documented bindings for the touch (`focaltech,ft8201`), amplifier (`awinic,aw87319`) and wireless (`qcom,wcn3660b`) parts, and the panel is a standard DRM panel driver. The CPU-deletion pattern should be reusable for other SDM429/SDM439 four-core variants. We have not yet submitted patches.

### 8.3 Threats to validity

- **Single Device & Operator:** Measurements are taken on a single SM-T295 unit across single runs by a single operator; no variance or confidence intervals are reported.
- **Boot Stage Mismatch:** Boot time stages for LineageOS do not sum to the reported total (Table 4, flagged explicitly).
- **Unverified Graphics Benchmark:** The graphics acceleration result is unverified, and the photographed desktop session in Figure 7a uses software rendering (llvmpipe).
- **Reproduction Guide Allocation:** The partition table lists the Linux-side roles; the final allocation of the Android-side partitions to LineageOS must be stated explicitly in the reproduction guide.
- **Static Telemetry Panel:** The menu's telemetry panel contains static text (for example a kernel version and battery capacity) that lags the running build.

## 9. Conclusion and Future Work

An abandoned, bootloader-restricted tablet can run a near-mainline Linux desktop and LineageOS 21 from one boot menu, with the factory bootloader left intact so recovery stays possible. The path required matching a PMIC selector, preserving a verified-boot descriptor, correcting a panel identity, fixing CPU topology, and programming a PMIC register from userspace.

Next steps are:
1. Hardware-accelerated graphics with documented and reproducible measurements (Freedreno on Adreno 504).
2. The camera pipeline (Galaxycore GC8034 rear, GC2375H front sensors).
3. A sensor bridge daemon for automated display orientation rotation.
4. Validated 4G LTE cellular data and SMS through ModemManager.
5. Repeated empirical measurements with variance metrics.
6. Upstream device-tree patch submission to the mainline Linux kernel.
